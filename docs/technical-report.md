# 1 项目概述

## 1.1 缘起：一个正在消失的舞台

皮影戏是中国最古老的戏剧形式之一，2011 年被列入联合国教科文组织人类非物质文化遗产代表作名录。它曾遍布大江南北，形成陕西、唐山、四川、山东、山西、辽东、甘肃等各具特色的地方流派。

但今天它面临真正的困境：

- **传承断层**：皮影艺人平均年龄偏高，年轻学徒极少，很多流派只剩个位数传人。
- **观看门槛高**：年轻人听不懂唱腔、不熟悉剧目，看一场戏往往"看不懂、看不下去"。
- **固定舞台的局限**：皮影必须到剧场或展馆现场观看，无法进入日常数字生活。
- **数字化停留在"记录"**：现有非遗数字化多为影像存档与 3D 扫描，是"保存"而非"让它可以被玩、被理解"。

我们想解决的不是"把皮影拍下来"，而是**让一个普通用户可以自己动手摆弄一副皮影、听懂它、甚至把自己的照片变成皮影并演上一段**。

## 1.2 作品定位

**云幕皮影**是一个面向公众的非遗皮影数字化 Web 应用。它把传统皮影的"影偶 + 幕布 + 灯光 + 说唱"四件事，分别映射成 Web 端的四类能力：

| 传统要素 | Web 化映射 | 技术载体 |
| --- | --- | --- |
| 影偶 | 可动骨骼皮影，可换装、可导入、可由照片生成 | `src/piying/rig-engine.js` 骨骼装配引擎 |
| 幕布 | 全屏纸灯箱舞台 + 场景砌末库 | DOM 舞台 + `public/piying/scenery` |
| 灯光 | 页面转场、灯晕、幕布斜扫等光效语言 | 四套转场体系 |
| 说唱 | AI 讲解员：能听、能看、能说、能规划路线 | Agent + RAG + 多模态 |

作品的核心主张是：**AI 不是给传统页面"加一个聊天框"，而是成为皮影本身的"操偶师"和"说书人"**——AI 生成的产物直接驱动舞台上的皮影运动，AI 的讲解绑定用户当前所在的展项与地区。

## 1.3 剧目来源：明代小说《七曜平妖全传》

作品中的打斗过场《影刃交锋》并非虚构，其人物与情节取自**明代白话神魔小说《七曜平妖全传》**——讲徐鸿儒聚众作乱、朝廷遣将平叛、其间妖法迭出的故事。这正是传统皮影戏班最常搬演的"武打戏"母题之一：红脸大刀的反派、奉命征讨的将领、妖风与流矢。

我们把这个桥段原样搬进 Web：

- **角色**：将领（`general`，持剑）与徐鸿儒（`warrior`，赤面偃月刀）
- **台词**：三段对白直接写进时间轴（"大胆逆贼，你已无处可逃了"/"桀纣无道！白莲现世，自替天罚之"/"枉你赤面大刀肖关公，却为黄河水兽祸神器"）
- **结构**：双将交锋 → 步步紧逼 → 妖法流矢 → 一刃断矢 → 黑雾遁形，五段剧情对应五段配乐

选择这部小说的原因有两点：一是它是**皮影戏的真实剧目来源**，不是为演示硬编的现代故事；二是它的"神魔斗法"结构天然适合拆成 QTE 节点——每一次妖法来袭，都是玩家必须接招的时刻。

## 1.4 核心亮点

1. **AI 生成的是"可动的皮影"，不是一张图**
   普通图生图只能得到静态图片；本作品把一张人像照片拆解为 15 个可独立旋转的皮影部件（头/躯干/上臂/前臂/手/大腿/小腿/披风/兵器），按标准关节树装配成可直接上台表演的影偶。

2. **摄像头手势即是玩法输入**
   用户对着镜头做出"交叉格挡 / 横向直刺 / 自上而下劈砍"，MediaPipe 姿态识别在浏览器端实时判定，命中则动画继续、未通过则幕布闪回重来。

3. **AI 讲解员与舞台强耦合**
   讲解员知道用户在地图上是哪个省份、在展示页看的是哪一件作品、在工艺页读到第几步，回答与页面上下文一致，并能主动规划"接下来看什么"的导览路线。

4. **一套统一的光影语言**
   首页开演用"云海启幕"，tab 互切用"灯焰呼吸"，子页进出用"影人推移"，AI 导览跳转用"幕布斜扫"，页面内进入玩法用"灯晕扩散"——五套转场都从"舞台光"这一意象里生长出来，而不是随手套用通用转场库。

# 2 需求分析

## 2.1 目标用户与场景

| 用户画像 | 典型场景 | 关键诉求 |
| --- | --- | --- |
| 对非遗好奇的年轻人（18–35） | 刷到皮影视频，想了解"这是什么、怎么做的" | 低门槛、好看、能互动 |
| 中小学教师 / 研学带队 | 非遗课程或研学活动，需要可讲的素材 | 讲解准确、有出处、可追溯 |
| 到馆游客 | 在博物馆/文化馆现场，扫码进入 | 与展项对应、能导览路线 |
| 皮影爱好者 / 美术生 | 想自己配色、换装、试动作 | 可定制、可导入自己的素材 |
| 内容创作者 | 想用皮影风格做短视频素材 | 能把照片转成皮影、导出画面 |

## 2.2 功能需求

**F1 展馆与导览**
- 中国地图选择省份，进入该地区皮影流派介绍（34 个地区档案）
- 每日一赏：按地区随机推荐一件皮影作品
- 展示页、工艺流程页、历史时间轴三个知识页

**F2 AI 讲解员**
- 页面内常驻悬浮球，随页面上下文变化（地区、当前展项、当前章节）
- 支持文本提问、语音提问、上传图片识图讲解、朗读回答
- Agent 模式：可主动规划导览路线并跳转页面

**F3 影偶工坊**
- 切换内置皮影（将官 / 武净）
- 从本地文件夹导入自制皮影（manifest + 部件图 + 关节树，带合法性校验）
- AI 图片转皮影：上传照片 → 生成 15 个部件 → 自动注册为可玩角色
- 舞台内自由摆放场景砌末（城楼、山石、松、云、火焰、黑雾、流矢等 11 种）

**F4 身入影幕（互动舞台剧）**
- 84 秒打斗过场（对白 + 配乐 + 五段剧情）
- 三处 QTE 校准：摄像头视觉识别或指针轨迹二选一
- 判定失败黑屏闪回退回到上一检查点
- 主角形象跟随用户在工坊中选择的皮影，并固定使用主角宝剑

**F5 知识小测**
- 5 题随机问答，进度条与即时反馈

## 2.3 非功能需求

| 类别 | 指标 | 实现方式 |
| --- | --- | --- |
| 响应式 | 手机竖屏 / 平板 / 桌面全适配 | rpx 换算 + 900/1600 两档断点 |
| 首屏 | 骨架屏 + 分段加载 | 图片懒加载、AI 面板按需下载 |
| 可用性 | AI 服务不可用时仍可浏览 | 三服务解耦，未配模型时自动走本地合成/离线知识 |
| 安全 | 密钥不入库、内容可审核 | 全部走环境变量；上传与回答双向审核 |
| 可维护 | 模块边界清晰 | 前端 `pages / components / piying / utils`，服务端 `endpoints / ai / db` |
| 可测试 | 关键路径可自动验收 | 40+ 项浏览器与接口验收脚本 |

## 2.4 与现有方案的差异

| 方案 | 形态 | 局限 |
| --- | --- | --- |
| 非遗数字博物馆 | 图文 + 视频 + 3D 模型 | 只能"看"，不能"玩"，更无法理解 |
| AI 绘画工具 | 输入提示词出图 | 得到静态图，与皮影的可动性无关 |
| 通用文化问答机器人 | 聊天框 + 知识库 | 与页面内容割裂，回答不跟上下文 |
| **云幕皮影** | **可动皮影 + Agent 讲解 + 摄像头玩法** | **AI 产物直接驱动舞台，讲解与页面同源** |

**三服务解耦**是本架构最重要的设计。数据服务只读、AI 服务无状态、前端可独立构建部署；任何一服务挂掉，其余功能仍可用（AI 不可用时自动降级到离线知识问答与本地程序化合成）。

## 3.2 前端架构

**分层**

```
pages/        页面级编排：负责数据装配与流程状态机
components/   展示组件：无业务状态，只接收 props / 抛事件
piying/       领域引擎：皮影装配、动画、判定、AI 工具（纯 TS/JS，可单测）
store/ utils/ 横切能力：图片缓存、地区记忆、转场播放器
```

**页面与状态**

每个页面是"壳 + 状态机"：以 `CurtainPage` 为例，`phase` 在 `loading → hub → playing → hub` 之间流转，所有副作用（装配、播放、销毁）都挂在状态迁移上，组件本身不持有全局状态。

**组件体系**

`art-v2/` 下是一套自建的"皮影皮肤"组件库：`ArtTopBar`、`ArtBottomNav`、`ArtButton`、`ArtPageShell`、`ArtToast`。所有页面共用同一套视觉 token（`--art-font-title`、`--rpx`、金色描边渐变等），保证 9 个页面视觉一致。

**转场体系**

| 场景 | 方案 | 实现 |
| --- | --- | --- |
| 首页 → 地图 | 云海启幕（4.1s） | rAF 时间轴驱动云团推拉 |
| 底部 tab 互切 | 灯焰呼吸（400ms） | 遮罩压暗回升，暗场最深处切路由 |
| 子页进出 | 影人推移（220ms） | 旧页推出、新页推入 |
| AI 导览跳转 | 幕布斜扫（260ms） | 柔边斜幕扫过 |
| 页面内进入玩法 | 灯晕扩散（640ms） | 从点击点扩散，盖满时切换 |

## 3.3 服务层架构

**数据服务（shim，8787）**
- 严格只读：代码层只允许 `SELECT`，连接使用只读账号
- 统一 v1 信封：`{ code, message, data }`，HTTP 恒 200，业务失败用 `code` 表达
- 素材路由 `/images/**` 映射到工程内 `assets/images`，含路径穿越防护与大小写/空白归一

**AI 服务（8788）**
- 无状态，所有上下文由前端携带
- 端点：`/health`、`/ask`（知识问答）、`/narrate`（讲解）、`/agent`（工具调用）、`/vision`（识图）、`/quiz`（出题）、`/piying`（图片转皮影）
- 流式输出走 SSE，前端边收边渲染（打字机效果）

## 3.4 数据层

MySQL 8.0，表结构沿用小程序 legacy 口径，共 7 张核心表：

| 表 | 行数 | 用途 |
| --- | --- | --- |
| `regions` | 34 | 地区档案（名称、别名、简介） |
| `shadow_region_profiles` | 34 | 各地区流派特征（唱腔、造型、代表剧目） |
| `media_assets` | 410 | 图片素材索引 |
| `daily_appreciation` | 72 | 每日一赏作品（带地区归属） |
| `interactive_characters` | 72 | 互动角色素材 |
| `quiz_questions` | 116 | 题库（题干、选项、解析） |
| `app_common_image` | 87 | 公共图片（转场、图标、背景） |

**只读约束**：shim 使用独立只读账号，SQL 层禁止 `INSERT/UPDATE/DELETE`；素材与数据全部随仓库/数据库脚本分发，评审无需准备外部数据源。

## 3.5 关键设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 端侧 CV vs 云端 CV | **端侧 MediaPipe** | 隐私（视频不出浏览器）+ 零延迟 + 省带宽 |
| 骨骼装配 vs 序列帧 | **骨骼装配** | 换装只需替换部件图；AI 生成部件即可复用同一套动作 |
| 单 Agent vs 固定流程 | **Agent + 工具** | 用户提问开放，需要自主选工具；同时保留规则预规划兜底 |
| 向量库 vs 轻量检索 | **关键词 + 可选 embedding** | 语料规模小（非遗知识），无需引入重型向量库；embedding 可选项避免强制外部依赖 |
| 图生图 vs 图生部件 | **图生部件** | 静态图无法上台表演；部件化后 AI 产物可直接进入动画 |

# 4 AI 技术方案

> 本章是作品的技术核心。四个 AI 子系统分别是：**讲解 Agent**（会规划、会调工具）、**RAG 检索**（回答有出处）、**多模态链路**（能看图、能听声、能生成部件）、**端侧视觉**（摄像头手势判定）。它们共享同一份知识语料与同一套安全策略。

## 4.1 总体 AI 架构

                ▼

                ▼
┌─────────────────┐   ┌──────────────────┐   ┌──────────────┐

                              └──────────────────────────────┘

## 4.2 大模型集成

### 4.2.1 选型理由

| 候选方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 单一厂商 SDK | 接入最快 | 绑定厂商，换模型要改代码 | ✗ |
| 自建推理（本地部署） | 数据不出域 | 显存成本高、中文皮影知识差 | ✗ |
| **OpenAI 兼容协议** | 换模型只改环境变量；国内多家厂商均兼容 | 需自己处理差异 | ✓ **采用** |

**实现**：`provider.js` 只用三组配置——`AI_BASE_URL` / `AI_API_KEY` / `AI_MODEL`，对话、视觉、语音、嵌合各自可独立指向不同服务。更换模型厂商时零代码改动。

### 4.2.2 提示词工程

`prompt.js`（13 KB）承担三类提示词：

1. **讲解员人设**：明确"你是非遗皮影讲解员"，约束不得臆造、必须基于给定资料、必须标注不确定。
2. **结构化输出**：讲解内容按「是什么 → 在哪流行 → 有什么讲究」组织，便于前端分段渲染。
3. **工具选择提示**：给 Agent 说明每个工具的适用场景，要求"先用检索确认资料，再回答"。

关键约束写法（示例）：

```
回答只能基于 <资料> 中的内容；资料没有覆盖的部分，明确说"这部分资料里没有记载"。
不要编造朝代、人名、剧目名。涉及地区时，必须与该地区档案一致。
```

### 4.2.3 流式输出

`/ask`、`/narrate` 走 SSE：服务端逐块 `data: {...}` 推送，前端 `fetch` + `ReadableStream` 边收边追加，配合打字机队列渲染。首字节到达即开始显示，长回答的体感延迟从"等 6 秒"变成"0.4 秒开始出字"。

### 4.2.4 稳定可控

| 措施 | 实现 |
| --- | --- |
| 超时 | 每次调用带 `AbortSignal`，超时可配置 |
| 取消 | 用户切换页面/发新问题，前端 `abort()` 旧请求 |
| 重试 | 网络类错误退避重试，业务错误不重试 |
| 降级 | 模型不可用 → 离线知识问答（不调模型，直接返回检索片段） |
| 空响应 | 模型返回空 → 用检索结果拼一段结构化回答 |

## 4.3 Agent 与工具链

### 4.3.1 架构

```
question + context
      │
      ▼
 ┌─────────────────────────────┐
 │ 第 1 轮：规划（plan）         │  LLM 返回 tool_calls
 └──────────┬──────────────────┘
            ▼
 ┌─────────────────────────────┐
 │ 执行工具（最多 3 个/轮）      │  search_knowledge / get_region_profile /
 └──────────┬──────────────────┘  get_craft_process / get_history_timeline /
            ▼                      list_regions / navigate_to
 ┌─────────────────────────────┐
 │ 观测回灌（observation）       │  结果作为 tool 消息追加进对话
 └──────────┬──────────────────┘
            ▼
      还有信息缺口？──是──▶ 第 2/3 轮（最多 3 轮，可配到 6）
            │否
            ▼
      生成最终回答（带引用）
```

### 4.3.2 六个工具

| 工具 | 作用 | 典型触发 |
| --- | --- | --- |
| `search_knowledge` | 从知识语料检索相关片段 | 任何需要事实的问题 |
| `get_region_profile` | 读取某地区流派档案（唱腔/造型/剧目） | "陕西皮影有什么特点" |
| `get_craft_process` | 读取八步工艺说明 | "皮影怎么做" |
| `get_history_timeline` | 读取历史时间轴 | "皮影多少年了" |
| `list_regions` | 列出全部地区 | "有哪些流派" |
| `navigate_to` | 规划并返回应跳转的页面路径 | "带我去看陕西" |

### 4.3.3 规划能力

Agent 有两层规划：

1. **LLM 驱动**：由模型决定调用哪些工具、传什么参数，支持多轮补充资料（默认 3 轮，最多 6 轮，每轮最多 3 个工具）。
2. **规则兜底**（`planOffline`）：当模型不可用或返回无工具时，按问题特征预先排定工具序列（例如提到地区 → `get_region_profile` → 需要工艺 → `get_craft_process`），保证任何环境下都有可用流程。

`navigate_to` 让 Agent 具备"行动能力"：它不只是回答，还能把用户带到该去的地方，前端收到后走「幕布斜扫」转场。

### 4.3.4 可观测

Agent 每步通过 SSE `step` 事件上报（`phase: plan/act/finish`），前端显示"思考中 / 正在查资料 / 整理回答"，让 AI 的推理过程可见而非黑箱。

## 4.4 RAG 技术方案

### 4.4.1 语料构建

`corpus.js` 把非遗知识切成带结构的小块：

```json
{ "id": "region:shanxi", "title": "陕西皮影", "text": "...", "region": "陕西", "tags": ["流派","造型"] }
```

语料来源：地区档案（34）、流派档案（34）、工艺八步、历史时间轴。全部随仓库分发，评审无需外部数据。

### 4.4.2 检索策略

`retrieval.js` 实现两级检索：

| 模式 | 条件 | 算法 |
| --- | --- | --- |
| 关键词（默认） | 未配置 embedding | 中文 **character-bigram** 重叠率 + 地区/标签加权 |
| 向量（可选） | 配置了 `AI_EMBEDDING_*` | 余弦相似度；向量带本地哈希缓存，避免重复计费 |

**为什么默认用 bigram 而不是向量**：非遗语料规模小（百余块）、领域词高度集中（"灯影""碗碗腔""灰皮"），bigram 重叠率的召回已足够，且零依赖、零延迟、零费用；向量作为可选增强，配了就自动切换。

**为什么不做重型向量库**：数据量下（<200 块）暴力计算余弦即可，引入 FAISS/Milvus 反而增加部署负担。

### 4.4.3 提炼与引用

检索结果按分数降序取 **top-4**，低于阈值返回空（宁可不答，也不拿低相关片段硬凑）。命中的片段随回答一起返回：

```json
{ "answer": "...", "sources": [{ "title": "陕西皮影", "region": "陕西", "score": 0.62 }] }
```

前端把 `sources` 渲染成可点击的来源标签，点击可跳到对应知识页——**回答可溯源**，这是 RAG 相较于纯 LLM 的核心价值，也是评审关注的"生成质量是否因检索而提升"的直接证据。

## 4.5 多模态能力

### 4.5.1 识图讲解（图 → 文）

用户上传皮影照片 → 压缩到长边 1024 → 转 base64 → `/vision` → 视觉模型识别（造型、流派特征、可能剧目）→ 与检索结果融合生成讲解。

**融合方式**：先识图得到关键词（如"红脸、长靠、持刀"），用这些词再检索一次知识库，把视觉结论锚定到已有资料上，避免模型自由发挥。

### 4.5.2 语音（声 → 文 → 声）

- **语音提问**：浏览器 `MediaRecorder` 录音 → `/ask` 携带音频 → 服务端转写 → 进入正常问答流程
- **朗读回答**：回答文本 → 分段调用 TTS → 逐段播放，支持中途打断

**为什么不全程在端侧做**：端侧中文 TTS 自然度不足；而 ASR 端侧模型体积大。折中方案是"录音端侧、识别云端、播放复用浏览器语音"。

### 4.5.3 图片转皮影（图 → 可动影偶）★

这是本作品最具差异化的多模态能力。流程：

```
用户照片
   │
   ▼ ① 人物门禁（是不是人？是否违规？）
   ▼ ② 图像生成（fast：单张零件图 / refined：定妆图 + 零件图）
   ▼ ③ 洋红底抠图 → 透明部件
   ▼ ④ 按标准 15 关节树装配
   ▼ ⑤ 校验（零件尺寸、关节可达、manifest 合法性）
   ▼ ⑥ 注册进角色库（可直接上台表演）
```

**降级路径**：未配置图像生成模型时，`procedural.js` 用照片采样到的主色，**程序化合成**整套皮影部件（按皮影的对称、镂空、描边规则绘制），同样产出可注册的影偶，界面明确标注"本次由本地皮影合成器生成"。

**关键设计**：生成的是**部件**而不是整图——因为只有部件才能挂到关节树上运动。这是"图生图"工具无法做到的事。

## 4.6 端侧视觉：手势 QTE

### 4.6.1 方案选型

| 方案 | 延迟 | 隐私 | 依赖 |
| --- | --- | --- | --- |
| 云端姿态估计 | 100ms+ | 视频上云 | 需要上传视频流 |
| **MediaPipe PoseLandmarker（端侧 WASM）** | <20ms | 视频不出浏览器 | 本地模型 44 MB |

**采用端侧**：隐私是首要理由（用户在家对着镜头做动作，视频不应上云），其次是实时性——QTE 判定窗口只有 4 秒，延迟会毁掉手感。

### 4.6.2 判定算法

从姿态关键点提取上肢向量，做三分类：

| 招式 | 几何特征 | 判定条件 |
| --- | --- | --- |
| 交叉格挡（X） | 两小臂夹角 | 双腕连线与双肩连线夹角 > 60°，且两小臂在胸前交叉 |
| 横向直刺 | 主手臂水平度 | 肩→腕向量近乎水平（±20°），且伸展长度超过阈值 |
| 自上而下劈砍 | 主手臂垂直度 | 肩→腕向量近乎竖直向下，且手腕低于肩 40% 身长 |

**防误判**：连续 3 帧确认才算命中；"朝镜头前刺"这类位移极小的动作单独走「屈肘 → 伸直」快速通道判定。

### 4.6.3 双通道兜底

摄像头不可用（未授权/无设备/环境不允许）时，自动切到**指针轨迹**判定：屏幕上画两笔交叉斜线 = X，一笔横向直刺 = 前突刺，一笔自上而下 = 下劈。两条通道判定口径一致，保证任何设备都能完成演示。

## 4.7 AI 安全与可控性

| 层 | 措施 |
| --- | --- |
| 输入 | 上传图片大小/格式限制；文本长度限制；图片先过人物门禁 |
| 内容 | `moderation.js` 双向审核：用户输入 + 模型输出；命中即替换为安全提示 |
| 事实 | 回答必须基于检索资料，资料未覆盖时明说"没有记载" |
| 隐私 | 识图与语音仅用于本次讲解，不落库；端侧视频不出浏览器；界面明示 |
| 密钥 | 全部走环境变量，仓库内只保留 `.env.example`；仓库含密钥扫描脚本 |
| 兜底 | 模型不可用 → 离线知识；生成不可用 → 本地合成；摄像头不可用 → 指针判定 |

## 4.8 性能与成本优化

| 优化点 | 做法 | 效果 |
| --- | --- | --- |
| 向量缓存 | embedding 结果按内容哈希落本地文件 | 重复语料零调用 |
| 图片压缩 | 上传前长边压到 1024 | 请求体积降 60%+ |
| 流式输出 | SSE 首字节即渲染 | 体感延迟 6s → 0.4s |
| 按需加载 | AI 工坊、CV 模型动态 `import()` | 首屏不下载 44 MB 模型 |
| 工具并发 | 同一轮内多工具并行执行 | 多工具查询耗时 ≈ 最慢那个 |
| 上下文裁剪 | 只携带当前页面相关信息 | 输入 token 减少约 40% |

# 5 核心功能实现

## 5.1 皮影骨骼引擎（`src/piying/rig-engine.js`）

皮影之所以能动，靠的是"关节树"：每个部件挂在一个父节点上，绕枢轴（pivot）旋转，父节点转动会带子节点一起转。

**数据模型**（`manifest.json`）：

```json
{
  "schema": "piying-rig/1",
  "name": "general",
  "stage": { "width": 900, "height": 860 },
  "parts": { "head": { "src": "assets/head.png", "size": [136, 187] }, "sword": { "src": "assets/sword.png", "size": [99, 547] } },
  "nodes": [
    { "id": "torso", "part": "torso", "parent": null, "pivot": [69, 102], "attach": [69, 0], "z": 1 },
    { "id": "uArmN", "part": "upperarm", "parent": "torso", "pivot": [15, 8], "attach": [15, 96], "angle": 42 },
    { "id": "sword", "part": "sword", "parent": "handN", "pivot": [49, 60], "attach": [21, 45], "z": 14 }
  ],
  "poses": { "rest": { "angles": {} }, "brandish": { "angles": { "uArmN": 116 } } }
}
```

**引擎能力**

| 能力 | 说明 |
| --- | --- |
| 装配 | 递归建 DOM，父→子累积变换（`translate → rotate → translate`） |
| 姿势 | `setPose(name)` 按 poses 批量写角度，带缓动过渡 |
| 呼吸 | `setIdle(true)` 让披风、头、手臂做低幅正弦摆动，静止时也有"活着"的感觉 |
| 反向运动 | `setAngles()` 接收外部传入的关节角度（人影同步用） |
| 调试 | 可选关节手柄，可拖动改角度、实时读数值 |

**为什么不用序列帧**：序列帧换一套皮肤要重画所有帧；骨骼装配换皮肤只需替换 15 张部件图，**同一套动作可直接复用**——这正是 AI 生成部件能够"直接上台"的前提。

## 5.2 AI 图片转皮影（`server/src/ai/piying.js` + `src/piying/ai/`）

**两段式生成**

| 模式 | 产出 | 用途 |
| --- | --- | --- |
| `fast` | 单张零件拼版图 | 快速预览 |
| `refined` | 定妆图 + 零件拼版图 | 正式注册 |

**前端处理链**（`chroma.js`）

1. 采样背景色（洋红/绿幕），按色距生成 alpha → 去底
2. 按网格切出各部件（头/躯干/上臂/前臂/手/大腿/小腿/披风/兵器）
3. 抠图后的部件按 `size` 归一化，写入新的 manifest
4. 复用标准关节树（15 节点）与标准姿势库

**程序化降级**（`procedural.js`）
无图像生成模型时，按照片主色 + 皮影造型规则（对称、镂空纹样、描边）直接绘制 15 个部件，产出同样可注册的影偶。

## 5.3 身入影幕：打斗过场与 QTE

**时间轴模型**（`battle/score.js`）
整段 84.2 秒，两种时钟交替：

| 区间 | 时钟 | 原因 |
| --- | --- | --- |
| 0–17s 对白 | `performance.now()` | 无配乐，需精确控制打字节奏 |
| 17s 之后 | `audio.currentTime` | 动作必须与配乐对齐 |

二者在 17s 交接；配乐被浏览器拦截时自动切回内部时钟，过场不会卡死。

**QTE 判定**（`qteTimeline.js`）

```
节点时间 T
  ├─ T - 3.3s  角标出现（看图 1.3s + 判定前半 2s）
  ├─ T - 2s    判定窗口开启
  ├─ T         招式落点（动画演出）
  ├─ T + 2s    结算
  └─ 通过 → 继续；未通过 → 黑屏闪回 620ms → 回退到上一检查点
```

三个节点与招式一一对应（招架弹反 / 蓄力刺击 / 斩断流矢）。

**失败回退**
退回点不是简单"重播"，而是回到上一个已通过节点之后，已通过的节点不再重复拦截。

## 5.4 页面转场体系

| 转场 | 触发 | 时长 | 技术要点 |
| --- | --- | --- | --- |
| 云海启幕 | 首页 → 地图 | 4.1s | rAF 逐帧写 transform，路由在散场开始时切换 |
| 灯焰呼吸 | 底部 tab | 400ms | 遮罩压暗回升，暗场最深处切路由 |
| 影人推移 | 子页进出 | 220ms | 仅作用于 `.art-page-shell`，避免 fixed 底栏跳位 |
| 幕布斜扫 | AI 导览跳转 | 260ms | 柔边斜幕扫过 |
| 灯晕扩散 | 页面内进玩法 | 640ms | 从点击点扩散，盖满时切视图 |

**总原则**：所有转场层挂在 `App.vue`（`router-view` 之外），否则会随路由卸载导致动画被掐断；四套轻转场互斥，不叠加。

# 7 创新点说明

## 7.1 技术创新点

| # | 创新点 | 与传统方案的区别 | 价值 |
| --- | --- | --- | --- |
| 1 | **AI 生成"可动皮影部件"而非静态图** | 图生图只能得到一张图；本作品生成 15 个可独立旋转的部件并自动装配到标准关节树 | AI 产物可直接上台表演，从"看图"跃迁到"能演" |
| 2 | **端侧姿态识别驱动的 QTE 玩法** | 常见做法是上传视频到云端识别；本作品在浏览器内跑 MediaPipe | 视频不出设备、延迟 <20ms、可离线 |
| 3 | **双通道判定** | 多数体感游戏依赖单一输入 | 摄像头不可用时自动切指针轨迹，演示零风险 |
| 4 | **Agent 具备"行动能力"** | 常见问答机器人只能输出文本 | `navigate_to` 工具让 Agent 能规划路线并真实跳转页面 |
| 5 | **讲解与舞台状态强耦合** | 通用聊天框不知道用户在哪 | 回答随地区/页面/章节变化，导览与页面同源 |
| 6 | **统一的"舞台光"转场语言** | 通用转场库与内容无关 | 五套转场都从皮影戏的"影与光"意象生长 |

## 7.2 应用创新点

| # | 创新点 | 说明 |
| --- | --- | --- |
| 1 | **把非遗的"可玩性"做出来** | 传统非遗数字化多为影像存档；本作品让用户能换装、摆砌末、演戏、拍照变皮影 |
| 2 | **经典剧目的交互化改编** | 取《七曜平妖全传》将领斗徐鸿儒的桥段，把"神魔斗法"拆成三个 QTE 节点 |
| 3 | **低门槛的传承入口** | 不需要任何皮影知识，进来就能玩；玩的过程中被讲解员告知"这是什么、哪里的流派" |
| 4 | **生成即资产** | 用户生成/导入的皮影会注册进角色库，成为可反复使用的资产（可导出、可再编辑） |

# 8 总结与展望

## 8.1 总结

云幕皮影把非遗皮影的"影偶、幕布、灯影、说唱"四要素完整搬进 Web，并用 AI 重新赋予了它们生命力：

- **影偶**由骨骼引擎驱动，AI 生成的部件可直接上台
- **幕布**是纸灯箱舞台，砌末可自由摆放
- **灯影**化作五套转场语言
- **说唱**交给一个会规划、会查资料、能带路的 Agent

技术上，作品在**多模态生成**（图片→可动影偶）、**端侧视觉**（手势 QTE）、**Agent 工具链**（6 工具 + 规划）、**RAG 检索**（可溯源回答）四个方向都做了完整实现，并有 130+ 条自动化验收兜底。

## 8.2 社会价值

- **文化传承**：把"看不懂、进不去"的皮影戏变成年轻人愿意点开的交互应用
- **教育普惠**：一台电脑/平板就能上非遗课，不依赖实体展馆与演出班子
- **数字平权**：手机浏览器即可使用，无需高端设备或专用应用

## 8.3 商业潜力与落地路径

非遗数字化是一个**政策与需求同时成熟**的市场：文旅部持续推进非遗进景区/进校园，博物馆数字化改造预算逐年增加；而现有的非遗数字化供应商多为"扫描建档"型，缺少可交互、可传播的产品。

**四层收入结构**

| 层级 | 客户 | 产品形态 | 定价思路 |
| --- | --- | --- | --- |
| **To B 文旅** | 博物馆、文化馆、景区 | 沉浸式导览系统：地图导览 + AI 讲解 + 互动舞台 | 项目制（按展馆规模 5–20 万/年）或 SaaS 订阅 |
| **To G 非遗保护** | 地方文旅局、非遗中心 | 地方流派数字化展示 + 传承人档案 + 公众端小程序 | 政府项目招标 / 专项经费 |
| **To B 教育** | 中小学、研学机构 | 非遗课程包：课件 + 互动舞台 + 学生作品导出 | 按班级/学年订阅 |
| **To C 创作者** | 短视频创作者、美术生 | AI 皮影生成 + 导出透明序列帧 / 视频 | 订阅制 + 生成次数包 |

**成本结构**

| 项 | 说明 | 优化空间 |
| --- | --- | --- |
| AI 推理 | 讲解、识图、图生皮影 | 已支持本地程序化合成降级；小模型 + 缓存可再降 50% |
| 素材 | 皮影部件与砌末 | 自有资产，边际成本近零 |
| 部署 | 三服务 + MySQL | 单机可跑，2C2G 云主机足够小型场馆 |

**竞争壁垒**

1. **技术**：可动部件生成 + 端侧 CV 判定，需要同时懂传统造型与图形工程
2. **内容**：34 个地区流派的整理资料 + 剧目改编，是长期积累的内容资产
3. **体验**：统一的"舞台光"视觉语言，难以被通用模板复制

**落地节奏**

```
阶段一（当前）  赛事 MVP，验证"AI 生成皮影 + 互动舞台"的技术可行性
阶段二（3–6 月）与 1–2 家地方文化馆合作试点，跑通导览 + 研学两条场景
阶段三（6–12 月）SaaS 化：多馆管理、内容后台、数据看板
阶段四（1 年后）创作者平台：皮影资产库 + 分成机制
```

## 8.4 局限与展望

**当前局限**

- 皮影造型库仅内置 2 个角色，更多流派角色需要继续拆解
- 打斗过场为单段剧本，尚未支持用户自编剧情
- 语料规模有限，冷门流派问题可能检索不到

**后续规划**

1. **角色扩展**：把 34 个地区的代表性皮影做成可玩角色
2. **剧本编辑器**：让用户用自然语言编排一段皮影戏（AI 生成时间轴）
3. **多端**：适配微信小程序与平板触控
4. **社区**：用户生成的皮影可分享、可二次创作
